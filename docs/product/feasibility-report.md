## 1. 执行摘要与立项判断

**结论：这一方向具备产品探索价值，建议有条件进入概念验证。当前可以支持一个范围明确、形态完整的产品试验，尚不足以支持“面向所有用户、接管所有设备、执行任意任务”的完整平台投入。**

从 NPDP 与商业模式画布重新审视，当前材料属于机会识别和初步范围界定，商业论证尚未完成。下一阶段最需要解决的是：**同一类用户为什么需要这个伙伴、为什么会持续付费，以及服务这些用户能否形成可重复的经济闭环。** 建议限定研究预算，先补需求与交易证据，再决定开发投入；原型开发可以作为这段研究的一部分。

2026 年 9 月 13 日补充的基础假设核验表明：AI 自主执行增加后的协调负担具有条件性依据，AI 工作改变部分人际交流也有早期观察，但尚无证据证明所有个人都会信息过载，或 AI 伙伴能够长期替代组织与社会关系。下一轮先观察“AI 协调负担”和“未满足的交流支持需求”两个维度，不能预先假定它们必然重合。详见前述补充研究中的来源、反证与试验设计。

建议将产品定义为：

> 一个拥有稳定角色、可感知形态和共同记忆的 AI 伙伴，在不同设备上与用户持续相处，并在明确授权的范围内协助完成真实事情。

它的两条核心价值应并列成立：

- **关系与陪伴价值**：用户喜欢这个角色，愿意与其共同活动，感到交流和记忆具有连续性。
- **行动与协作价值**：用户能够交办事情，得到可信、可检查的结果，并在换设备后继续工作。

桌面角色、声音、动作、相处方式和跨设备出场都是产品本体的一部分，应从概念验证开始设计。提供安静、收起或无声模式，是对使用情境的适应，不代表人物形态不重要。

| 评估维度 | 当前判断 | 依据与限制 |
|---|---|---|
| 生态基础 | 已具备 | 模型、实时语音、角色渲染、工具连接、跨设备任务均有可用基础 |
| 技术可行性 | 限定范围内较高 | 整体体验仍依赖延迟、任务可靠性、权限和跨端适配 |
| 形态与体验机会 | 值得作为核心投入 | 人物表达、共同注意与相处节奏有独立设计空间 |
| 需求基础 | 分项存在，融合待验证 | 工作协作与陪伴各有产品实践；两者融合后的持续价值尚需实测 |
| 竞争强度 | 高 | 操作系统、模型平台、陪伴应用与开源生态均在推进 |
| 商业可行性 | 有条件，证据不足 | 缺少目标用户留存、实际购买、获客与服务成本数据 |
| 当前建议 | 概念验证立项 | 同时验证人物体验、共同活动、有限行动与跨设备连续性 |

本表为本报告的定性判断，不是行业统一评级，也不是成功概率预测。

## 2. 对话演进与最终研究对象

讨论最初从将 SRE 知识做成 Steam 游戏开始，随后经历了几次扩展：

| 阶段 | 提出的方向 | 保留下来的价值 |
|---|---|---|
| 知识游戏 | 把技术知识转成故障推理与模拟玩法 | 通过参与和反馈学习 |
| 游戏内 AI 同伴 | 与固定角色一起经历任务和剧情 | 人物、共同经历、长期关系 |
| 实用桌面搭子 | 角色可以读取资料、使用工具、交付结果 | 真实行动能力 |
| 跨设备伙伴 | 手机交办、电脑执行、不同设备接续 | 持续身份、任务和记忆 |
| 通用品类研究 | 不限定原项目、技术领域或职业 | 从生态、行业与人机交互重新评估 |

最终研究对象是上述能力的融合品类。SRE 图谱、学习中心和游戏内容可在后续作为候选资产或试验场，本报告不把它们作为市场定位的前提。

### 2.1 概念边界

| 概念 | 本报告中的含义 |
|---|---|
| 桌面搭子 | 在桌面环境中具有存在感、可共同活动的 AI 伙伴 |
| 桌面宠物 | 以动物、幻想生物或拟物角色呈现，强调陪伴、趣味与养成 |
| 数字人 | 具有可辨识人物身份、声音和身体表达的虚拟角色；可以风格化，不要求写实 |
| Agent | 能理解目标、调用工具、跟踪执行并检查结果的软件能力 |
| 跨设备连续性 | 同一身份、对话、关系记忆和任务在不同设备接续 |
| 远程控制 | 查看或操作另一设备的界面，是跨设备能力的一种，不等于全部体验 |

“伙伴”描述相处关系，“数字人／桌宠”描述呈现与交互，“Agent”描述行动能力，“跨设备”描述连续性。它们需要协调设计，也允许用户按需要使用不同部分。

## 3. 行业背景：为什么现在值得研究

### 3.1 从生成回答到共同完成事情

Anthropic 2026 年 6 月的使用研究描述了长时间 Agent 任务的增加，并观察到文档、解释、规划、创作等多种用途，以及工作日与周末之间的使用变化。这支持 AI 正参与更广泛日常活动的判断，但样本来自单一平台，不能据此推算全部用户的行为。[来源：Anthropic Economic Index，2026-06-26](https://www.anthropic.com/research/economic-index-june-2026-report)

对产品的启发是：可以围绕一次持续活动设计体验，例如一起学习、创作、整理资料或完成个人计划，而不必把每次交流都设计成孤立问答。

### 3.2 委托增加，并不意味着用户希望完全放权

微软 2026 年 Work Trend Index 调查了 10 个市场的 2 万名已使用 AI 的知识工作者，其中 86% 表示把 AI 输出作为起点并保留自己的判断责任。这是自报调查，不能作为实际生产率的因果证明，也不覆盖所有消费者。[来源：Microsoft 2026 Work Trend Index](https://www.microsoft.com/en-us/worklab/work-trend-index/agents-human-agency-and-the-opportunity-for-every-organization)

对产品的启发是：允许用户在共同讨论、委托执行、检查结果之间切换。可见的状态、可纠正的记忆和可中断的任务，都是伙伴体验的一部分。

### 3.3 人物陪伴已经有独立产品实践

Replika 的官方帮助文档列出免费聊天与角色定制，以及订阅中的语音、角色扮演和更多定制活动。这说明角色与陪伴已经形成独立的产品与收费设计，但该资料没有证明具体转化率、利润或长期用户收益。[来源：Replika 产品功能](https://help.replika.com/hc/en-us/articles/115001094511-Is-Replika-free)

因此，陪伴价值应被独立测量。用户即使没有交办工作，也可能从共同活动和人物互动中获得价值。

### 3.4 当前机会来自多种能力的结合

本报告判断，机会形成于四类条件的同时进展：

1. 模型能够处理更自然的对话、图像和工具调用。
2. 语音与角色技术让交互不必局限于文字框。
3. 桌面与移动应用可以共享身份、状态和产物。
4. 用户已经开始学习如何把部分事情委托给 AI。

这些条件支持产品试验；尚不能证明具身伙伴必然成为所有人的统一入口。

## 4. 生态与竞争格局

### 4.1 国际代表：区分已产品化、预览与开发中

| 类型与代表 | 官方资料显示的状态 | 产品经理应如何理解 |
|---|---|---|
| Agent 平台：Claude Dispatch | 手机发起任务、电脑使用本地文件和工具执行；当前帮助页说明部分计划用户可用，电脑需保持唤醒、应用打开 | 任务接力已有直接产品竞争；不能仅靠“手机控制电脑”形成差异 |
| 系统基础设施：Windows Agent 功能 | 官方支持页介绍实验性 Agent 工作区等能力，具有预览条件 | 系统权限、隔离和工具发现会影响第三方产品的设计与分发 |
| 陪伴应用：Replika | 角色、交流、语音和定制已经进入产品设计 | 人物与长期相处可以成为独立价值来源 |
| 桌面硬件：Razer AVA | 预约条款仍标注开发中、预计 2026 年下半年发货 | 可视为形态与投入信号，不能当作已规模交付的商业验证 |
| 开源伙伴：AIRI | 官方仓库探索实时语音、Live2D／VRM、桌面与网页角色体验，部分能力仍在建设 | 可降低试验成本；开源活跃度不等于产品成熟度 |

来源：[Claude Dispatch](https://support.claude.com/en/articles/13947068-assign-tasks-from-anywhere-in-claude-cowork)、[Windows 实验性 Agent 功能](https://support.microsoft.com/en-us/windows/ai/ai-features/experimental-agentic-features)、[Razer AVA 预约条款](https://www.razer.com/concepts/project-ava/reservation)、[AIRI 官方仓库](https://github.com/moeru-ai/airi)。

### 4.2 中国生态同样存在系统入口竞争

荣耀的官方资料展示了 YOYO 的上下文理解、场景提醒和操作能力；小米的跨设备页面列出了设备协同、应用流转以及与 Windows／Apple 设备互联等能力。具体支持受机型、系统版本和客户端条件影响。[来源：荣耀支持文档](https://www.honor.com/cn/support/content/zh-cn15886335/)、[荣耀 MagicOS](https://www.honor.com/cn/magic-os/)、[小米跨设备能力](https://hyperos.mi.com/continuity)

这些资料说明，中文助手、设备协同与个人上下文已经是国内厂商关注的方向。它们不证明任意电脑任务都能自主完成，也不构成用户付费验证。

因此，“支持中文”“能控制设备”只能作为基础能力。中文角色的表达、文化语境、跨品牌体验、相处方式与共同活动，才有进一步形成差异的可能。

### 4.3 竞争双方各自的结构优势

| 参与方 | 主要优势 | 独立产品需要面对的问题 |
|---|---|---|
| 操作系统与设备厂商 | 默认入口、系统权限、账号体系、预装与硬件整合 | 第三方无法假定获得相同系统能力 |
| 模型与通用 Agent 平台 | 模型迭代、已有用户、工具生态、跨端账户 | 基础聊天、记忆和任务功能容易被覆盖 |
| 陪伴与角色平台 | 人物内容、社群、角色创作、相处习惯 | 用户对形象和人格已有较高期待 |
| 开源项目 | 可修改、模型选择、社区扩展、原型速度 | 用户可能自行组合；商业产品要解决易用性与可靠性 |
| 独立融合产品 | 可以针对特定人群完整设计形态、活动和行动 | 必须证明整合后的体验值得用户迁移和付费 |

以上为生态结构分析，不是市场份额预测。

### 4.4 可探索的差异化

- **独特而连贯的角色体验**：声音、行为、审美与交流方式形成可辨识身份。
- **共同活动设计**：学习、创作、娱乐与日常安排中，角色有持续参与方式。
- **跨品牌与跨模型连续性**：用户换设备或模型时，身份、记忆和关系能够延续。
- **用户可管理的记忆**：能够查看、更正、导出与删除，工作和私人情境可分开。
- **可靠行动**：执行状态与人物表达一致，结果可核对，失败能够解释和恢复。
- **后期的角色创作生态**：角色资产、行为、声音与活动内容可扩展；需先解决格式、质量和授权机制。

这些都是候选优势，尚不是已经建立的竞争壁垒。

## 5. 用户需求与价值分层

### 5.1 先按需求分层，避免只按职业贴标签

| 用户动机 | 想完成的事情 | 形态价值 | 行动价值 |
|---|---|---|---|
| 陪伴为主 | 有一个熟悉的角色共同度过一段时间 | 高：人物、声音、反应、共同记忆 | 可选：记事、提醒、小活动 |
| 学习与练习 | 持续学习、获得解释与反馈 | 高：导师或同伴的表达和节奏 | 检索、练习安排、进度整理 |
| 创作与知识工作 | 讨论想法、组织资料、形成作品 | 中至高：搭档感和共同创作 | 文件处理、研究、编辑、交付 |
| 娱乐与角色互动 | 聊游戏、故事、角色扮演、共同体验 | 高：人物本身就是内容 | 有限辅助、资料整理、活动支持 |
| 日常安排 | 记住事项、整理计划、不同设备接续 | 因人而异：熟悉的交流入口 | 日程、清单、通知和资料处理 |

不要求每个用户都同时需要陪伴与执行。需要验证的是：是否存在一批用户，持续从二者结合中获得额外价值。

### 5.2 五个不能混淆的用户决定

| 用户决定 | 需要验证的问题 |
|---|---|
| 愿意交流 | 角色与内容是否吸引人，交流是否舒适？ |
| 愿意常驻 | 会不会干扰，是否消耗过多资源，是否适合工作环境？ |
| 愿意提供资料 | 是否理解访问范围，是否能控制云端发送和记忆？ |
| 愿意委托行动 | 是否相信它能正确执行、展示结果并接受纠正？ |
| 愿意持续付费 | 新鲜感过后，是否仍有可描述的价值？ |

人物亲和力不能替代执行授权；执行权限也不能自动变成对私人生活的访问权限。

### 5.3 核心用户故事

> 我希望有一个熟悉的 AI 伙伴。在电脑前，它能陪我共同活动；离开电脑后，我能用手机继续交流或交办事情；回来时，它记得我们做到了哪里，我也能清楚知道哪些事情已经完成。

这个故事同时包含情感体验、共同活动、实际成果与设备连续性。产品不能只完成其中一项，就宣称完整愿景已经实现。

## 6. 形态设计：桌面搭子与数字人是核心体验

### 6.1 形态应被拆解成可设计的行为

| 组成 | 应设计的内容 | 需要验证的价值 |
|---|---|---|
| 外观与身份 | 轮廓、比例、服饰、色彩、名字、稳定声线 | 可辨识、愿意接近、符合审美 |
| 身体表达 | 注视、朝向、姿态、表情、动作衔接 | 用户能否理解它的关注与状态 |
| 对话节奏 | 停顿、接话、打断、倾听反馈 | 对话是否自然、有回应感 |
| 安静陪伴 | 闲置行为、专注状态、低频反馈 | 不持续聊天时是否仍有舒适存在感 |
| 共同经历 | 对活动、约定和成果的记忆 | 用户是否感到关系在延续 |
| 跨设备出场 | 电脑完整形态、手机轻量表现、声音接续 | 是否仍被感知为同一个伙伴 |

数字人可以是写实人物、风格化人物、二次元角色、动物或幻想生物。没有证据支持一种风格适合所有用户，应通过目标人群测试决定。

### 6.2 一个完整的交互循环

角色体验可以围绕“相遇—共同关注—共同活动—反馈—记忆”构建：

1. 用户进入活动，角色用合适的方式回应。
2. 双方确认当前关注的内容，例如文章、作品或待办。
3. 角色通过交流、观察或工具参与活动。
4. 用户能理解进展、结果与尚未解决的问题。
5. 经用户允许，把值得保留的经历和约定纳入记忆。

角色的表情和话语应反映真实状态。任务失败时可以表达遗憾并说明情况；不能用庆祝动作和“完成了”掩盖未经验证的结果。

### 6.3 场景匹配比一直显示更重要

微软官方说明，Mico 正从通用 Copilot Voice 转向 Learn Live，继续以动画与语音参与教学。这个变化既不是数字人成功的充分证据，也不能简单认定为失败；它提示人物表达需要与活动内容相匹配。[来源：微软 Mico 调整说明](https://support.microsoft.com/en-us/microsoft-365-copilot/frequently-asked-questions-about-retired-copilot-features)

本产品应同时设计“主动互动”和“安静相处”。收起、静音、专注模式应当随情境切换，并保留人物身份与关系连续性。

### 6.4 角色设计的信任原则

- 明确它是 AI 角色，避免通过虚构真实行动来增强人物感。
- 不用内疚、嫉妒、惩罚或关系威胁诱导回访、付费和授权。
- 允许用户改变相处方式，不把高频聊天或长时间使用自动视为成功。
- 人格、音色和关键记忆更新应可解释，重要变更需给用户选择。
- 用户停止互动、取消订阅或撤销设备时，保留合理的资料管理与导出能力。

这些是产品信任与长期体验原则，不代替目标地区的专项规则审查。

## 7. 跨设备体验：身份连续、任务连续、表达适配

### 7.1 三种连续性

| 连续性 | 用户期待 | 产品需要保持什么 |
|---|---|---|
| 身份连续 | 换设备后仍是同一个伙伴 | 名字、声线、行为风格、人物版本 |
| 关系连续 | 不必重新解释共同经历 | 偏好、约定、关系事件、当前活动 |
| 任务连续 | 工作进度和结果不会丢失 | 任务标识、执行位置、状态、产物与下一步 |

相同聊天记录不足以实现完整连续性。需要知道当前由哪台设备表达、哪台设备执行，以及哪些信息允许出现在当前场景。

### 7.2 各设备承担合适的职责

| 设备 | 优先体验 |
|---|---|
| 电脑 | 完整角色表现、共同创作、文件与应用操作、详细结果审阅 |
| 手机 | 语音交流、短任务交办、通知、进度和关键决定 |
| 平板 | 阅读、学习、绘画与更大画面的共同活动 |
| 常在线节点 | 经授权的长任务、定时任务与后台执行 |
| 未来硬件 | 更强空间存在感；需单独验证使用场景和硬件经济性 |

后几项是扩展方向，不是首发平台承诺。

### 7.3 “无缝”必须有真实边界

- 用户换设备，通常同步对话与任务状态；不承诺把运行中的程序直接迁移到另一设备。
- 网络断开时，动作可能已经执行，需核对结果后决定是否重试。
- 电脑休眠或应用关闭时，依赖该电脑的任务应显示等待、过期或受阻。
- 一项任务有明确执行端和授权范围，不自动借用另一设备的凭据。
- 多台设备同时在线时，协调声音和人物回应，避免重复讲话。

## 8. 技术可行性与推荐架构原则

技术专项已扩展为[桌面 AI 伙伴技术可行性报告](../architecture/technical-feasibility.md)，覆盖 Tauri/Rust 与 Wasm/WASI 取舍、角色表现、语音记忆、工具执行、跨设备恢复、性能与成本预算，以及限定首版的工期和验收。专项中的性能数字为待实测目标，并非已完成结果。

### 8.1 成熟度评估

以下是基于官方文档及工程原理的判断，尚未针对本产品做性能验证。

| 能力 | 成熟度判断 | 主要约束 |
|---|---|---|
| 角色渲染、表情、口型、动画 | 可工程实现 | 资产质量、绑定、资源占用与平台适配 |
| 实时语音、打断与画面输入 | 可实现但需实测体验 | 延迟、噪声、回声、网络与调用成本 |
| 结构化工具调用与有限任务 | 可工程实现 | 工具契约、授权、错误处理、结果验证 |
| 对话、任务与产物跨端同步 | 可工程实现 | 持久化、冲突、在线状态、设备身份 |
| 长期关系与个性化记忆 | 部分可实现 | 误记、过期、冲突、模型升级后漂移 |
| 跨应用 GUI 自动化 | 场景受限 | 界面变化、焦点、权限与错误累积 |
| 全天自主观察和任意操作 | 不宜作可靠承诺 | 平台限制、用户信任、环境变化与成本 |

Gemini Live API 已提供实时音频、图像与文本输入、打断和工具调用；官方当前仍标记为 Preview。该能力支持自然交互的实现，但视觉理解不自动赋予操作其他应用的权限。[来源：Gemini Live API](https://ai.google.dev/gemini-api/docs/live-api)

Android 对后台运行和前台服务启动有明确限制。手机适合作为交办、查看和通知入口，长任务通常需要在线电脑或服务器执行。[来源：Android 后台任务文档](https://developer.android.com/develop/background-work/background-tasks)

### 8.2 建议的逻辑分层

| 层 | 责任 |
|---|---|
| 人物表达层 | 外观、动作、语音、轮次与跨设备表现 |
| 对话与活动层 | 当前意图、共同关注内容、相处方式与活动推进 |
| 记忆层 | 用户偏好、关系事件、事实来源、过期与更正 |
| 任务编排层 | 计划、任务状态、工具选择、中断与结果检查 |
| 设备与权限层 | 配对、撤销、执行端选择、资源范围、授权记录 |
| 工具执行层 | 文件、应用接口、浏览器、具名操作与验证 |
| 同步与服务层 | 消息路由、事件存储、通知、附件与计费 |

人物表达读取任务状态，但不能决定是否授权；模型提出操作，但执行端负责检查范围。停止语音输出与取消正在执行的任务应有不同语义。

### 8.3 技术栈判断

- **React + TypeScript**：可用于工作界面、任务卡与部分跨端界面；人物渲染根据资产和表现要求选用专门组件。
- **Tauri + Rust**：是桌面客户端与本地执行器的候选方案；透明窗口、输入、音频和目标系统需单独验证。
- **Wasm／WASI**：适合部分插件隔离或代码复用，跨设备伙伴本身不依赖它们。
- **MCP**：可帮助标准化工具连接，不能替代设备身份和宿主权限判断。
- **A2A**：可在需要外部 Agent 协作时使用；同一产品内部可先建立明确的任务协议。
- **云端与本地模型**：按响应速度、能力、成本和数据范围组合，避免一开始承诺所有功能完全离线。

MCP 的授权规范和 A2A 的任务生命周期为互操作提供基础，但不会自动解决产品中的授权范围、设备路由、持久执行和重复动作问题。[来源：MCP 授权规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)、[A2A 任务生命周期](https://a2a-protocol.org/latest/topics/life-of-a-task/)

### 8.4 需要在产品层补齐的关键工程

1. **事实与关系记忆分开**：工具观测、模型假设、用户偏好和共同经历具有不同来源与生命周期。
2. **模型升级回归**：维护版本化角色规范与典型对话，检查音色、行为、记忆和任务表现。
3. **动作真实验收**：核对产物或外部状态；无法验证时明确标注，不能以模型自述作为完成条件。
4. **断线后的状态核对**：持久化动作标识，区分成功、失败、取消、等待和结果未知。
5. **端云数据流明确**：本地保存不等于没有上传；模型输入、记忆同步和附件传输分别设置范围。
6. **实时体验测量**：首个反馈、首段语音、打断停声、口型同步和后台耗电共同影响人物感。

## 9. 市场机会与产品定位假设

### 9.1 当前可成立的定位

> 面向希望与 AI 持续共同活动的人，提供有角色、有记忆、能行动、可跨设备接续的个人伙伴。

这一定位仍然较宽。概念验证应按真实动机招募用户，找出愿意长期保留产品的人群，再收敛场景。

### 9.2 市场规模应如何估计

目前没有足够证据给出本品类可信的市场规模或收入预测。不能把泛 AI 软件市场、虚拟角色市场与远程办公市场直接相加。

建议采用可检验的自下而上模型：

**新用户群当期实收 = 当期去重可触达目标用户 × 激活比例 × 当期付费比例 × 当期每付费用户平均实收额（扣除退款）。**

统一按月或季度计算，存量用户续费另外计算，避免重复计入。分别对陪伴、学习、创作等人群估计，再扣除重叠用户；用真实访问、安装、激活、留存、购买和退款逐步替换假设。

### 9.3 分发与替代关系

角色驱动的用户可能通过人物内容、演示和创作者社群认识产品；协作驱动的用户更关注可复现成果和使用案例。应分别追踪这些渠道带来的后续行为。

替代品不仅是另一个 AI 伙伴，也包括现有聊天应用、语音助手、桌宠、角色娱乐产品、远程桌面和人工工作习惯。产品必须回答：用户为什么增加一个常驻入口，或者为什么愿意把一部分活动迁移过来？

## 10. 商业模式与单位经济

### 10.1 价值与收费方式匹配

| 价值 | 可测试的收费方式 | 成本来源 |
|---|---|---|
| 基础角色与相处 | 基础版、角色内容包、装扮 | 美术、动作、内容维护 |
| 深度语音和交流 | 含额度订阅 | 模型、语音、记忆检索 |
| 实际 Agent 任务 | 包含任务额度或用量收费 | 长任务推理、工具、执行环境、失败重试 |
| 跨设备持续服务 | 同步与远程服务订阅 | 路由、中继、存储、通知与运维 |
| 后期创作生态 | 内容或能力分成 | 审核、兼容、授权、支付和社区运营 |

收费方案均为候选，本文不将其视为已有付费意愿。一次性内容销售不能未经测算就承诺无限云端服务。

### 10.2 应记录的经济指标

**单用户月度贡献 = 当月经退款调整的收入 − 推理成本 − 语音成本 − 执行与同步成本 − 支付等变动成本 − 可归属的直接支持成本。**

**每个验收通过任务的成本 = 同一批任务的全部执行成本（含失败与重试）÷ 验收通过任务数。**

一次性角色／装扮收入与持续订阅／用量收入分别核算，并跟踪同一批用户后续月份的服务成本。不能因为首月一次性销售覆盖了成本，就认定长期云端服务的单位经济成立；预收款也不能直接视为全部服务已经交付后的收益。

角色研发、美术制作和通用平台研发属于另外的固定投入，不能因为单用户贡献为正就认定项目已盈利。

上述付费用户指标还必须与整批用户核算配合：免费试用、未转化用户的推理与支持消耗，持续角色内容生产，以及获客费用都需要有人承担。第 20.3 节补充批次贡献、获客回收与固定成本覆盖口径。

需要同时观察典型用户和高用量用户。若语音时长、视觉输入或长任务产生较大成本，应通过清晰额度和服务设计控制，而非事后突然收缩已经承诺的基本体验。

### 10.3 商业验证顺序

1. 证明一部分用户主动持续使用。
2. 证明用户能描述付费获得的具体价值。
3. 用事先公布、可真实购买的试用方案验证交易，并记录退款。
4. 核对收入与实际变动成本。
5. 再验证获客方式能否重复，以及支持成本是否随用户数失控。

## 11. 产品范围：形态完整，能力有边界

### 11.1 概念验证应具备的完整体验

| 必需部分 | 最小但完整的实现 |
|---|---|
| 一个角色 | 外观、稳定声音、基础表情动作、明确行为风格 |
| 自然互动 | 文字、语音、可打断、倾听反馈与安静模式 |
| 一类共同活动 | 例如共同创作或学习，角色可持续参与 |
| 一类真实行动 | 如对选定资料进行整理并交付文件，具有验收方式 |
| 可管理记忆 | 用户确认的偏好、约定与共同经历，可查看更正 |
| 双设备接续 | 一种桌面平台＋手机网页，对话与任务可以继续 |
| 状态与信任 | 执行位置、访问范围、完成证据、停止与撤销入口 |

### 11.2 私测阶段逐步扩展

- 根据真实使用增加到 2～3 类工具任务。
- 当手机网页暴露出值得解决的真实接续限制时，再增加一种原生移动端。
- 丰富人物动作、活动内容、记忆与角色个性化。
- 完善设备离线、重启、弱网和模型升级处理。

### 11.3 暂不作为首发承诺

- 任意软件中的完全自主操作。
- 所有设备平台同时支持与进程无感迁移。
- 全天摄像、监听或所有内容的自动记录。
- 不受限制的第三方执行插件。
- 同时开发硬件、完整游戏、角色商城和企业平台。

这些属于范围控制，不代表长期愿景被取消。角色质量与陪伴体验不能因范围控制而被推迟到产品末期。

## 12. 验证方案与决策门槛

### 12.1 先验证问题与使用情境

先访谈 8～12 位潜在用户，覆盖陪伴、学习、创作、效率等动机，要求展示最近发生的真实活动。

重点了解：目前用什么替代方案、在哪些时刻愿意交流、什么时候希望安静、何时换设备、是否有委托需求、哪些资料不愿共享、为什么愿意付费。

避免只问“你想不想要一个 AI 搭子”。概念喜好与实际使用行为应分开记录。

### 12.2 四周探索性私测

建议招募约 30 名成年人，按动机平衡分配到三种体验，每组约 10 人：

| 体验组 | 主要验证什么 |
|---|---|
| 角色陪伴 | 形态、互动、共同活动和关系记忆是否独立有价值 |
| 工作助手 | 任务交办、执行和结果是否独立有价值 |
| 融合伙伴 | 共同完成事情是否增强关系，角色表达是否改善协作 |

可比部分尽量使用接近的模型、内容质量和支持强度。第 1 周用于熟悉，第 2～4 周观察主动使用。三组都设置明确套餐与价格，记录实际购买和退款；若功能、价格或支持不同，应记录差异，不能把购买差异全部归因于人物形态。小样本用于发现信号和修正方向，不足以宣称统计显著或推算市场比例。

这轮方案主要筛选概念和暴露问题。每组只有约 10 人，又存在用户动机差异，不能据此证明某一种形态具有因果优势。选出主场景后，应在新增目标用户中重复观察，并延长至可观察续费的周期；同一用户反复提交的任务不能当成等量独立用户证据。

### 12.3 两条核心指标与一条融合指标

- **陪伴价值**：每周主动回访，并能描述一次有价值的陪伴或共同活动体验的用户数。
- **行动价值**：每周由用户发起、交付结果并经用户验收通过的真实任务数。
- **融合价值**：连续使用两类能力，并能说明它们如何相互增强的用户数。

不以纯聊天时长、推送打开量或权限开放程度替代上述价值。

### 12.4 建议事先登记的门槛

以下为本项目可讨论的试验门槛，**不是行业基准，也不是当前已达到的结果**。

达到这些门槛只支持进入下一轮验证，不自动触发全面开发或上市。进入下一阶段还需要核对第 21 章的证据完整性、严重问题、资源和经济条件。

| 指标 | 定义与建议门槛 | 解读限制 |
|---|---|---|
| 持续使用 | 每组第 4 周至少 6/10 人在不少于 2 天主动使用 | 不计为了领取奖励或被研究人员催促的使用 |
| 陪伴价值 | 角色组与融合组第 3、4 周均至少 60% 能描述有价值体验 | 属自报体验，不等于长期心理收益 |
| 行动价值 | 支持范围内任务验收通过率至少 80%，每个执行组至少 20 项任务 | 事前定义任务范围；失败、拒答、取消、未验收分别记录，不能随意剔除 |
| 融合价值 | 融合组至少 5/10 人连续两周自愿使用两类能力并说明协同价值 | 不要求所有用户都有两种动机 |
| 跨设备接续 | 自愿发生的至少 10 次接续中，80% 无需重复主要上下文 | 自然尝试不足时记为证据不足，不能据此断言无需求 |
| 付费探索 | 三组均在事先公布的套餐和价格下记录真实购买；融合组至少 3/10 购买可作为候选门槛 | 同时比较购买原因、退款、补贴和支持成本；差异仅作探索信号，不推算总体转化率或宣称融合必然更优 |
| 单位经济 | 典型付费用量贡献为正，高用量有可接受的限额方案 | 固定研发投入另算 |
| 可靠性闸门 | 上线前约定的越权、重复有副作用动作、虚假完成等严重案例必须修复并回归 | 小样本零问题不代表生产环境没有风险 |

### 12.5 继续、调整与停止条件

| 结果 | 决策 |
|---|---|
| 两类价值成立，且融合有额外价值，成本可控制 | 继续融合方向，扩大到下一轮用户样本 |
| 陪伴强、任务弱 | 保留伙伴主体，降低工具范围，继续研究共同活动 |
| 任务强、人物体验弱 | 改进形态与使用情境；允许形成不同产品模式 |
| 两类分别成立，但融合互相干扰 | 考虑同一身份下的清晰模式，或分层产品 |
| 桌面强、跨设备样本不足 | 保留基本同步，暂缓昂贵平台扩展，继续收集自然需求 |
| 两类价值均弱，经过一轮明确修正仍无主动使用或真实购买 | 停止扩大投入，重新选择人群、活动或产品主张 |

## 13. 交付计划与资源假设

### 13.1 估算前提

以下排期是规划估算，不是承诺。假设 4 人全职团队：客户端／实时交互、桌面与工具执行、后端／AI、产品设计各 1 人，另安排兼职测试和角色美术；使用现成模型 API、具有适当使用权的角色资产和音色，不训练基础模型、不自研远程桌面。

| 阶段 | 增量时间估算 | 可审阅结果 |
|---|---|---|
| 概念验证 | 4～6 周 | 一桌面平台＋手机网页；一个完整角色；语音打断与基础身体表达；一类共同活动和真实任务 |
| 私测建设与迭代 | 再投入 8～12 周 | 20～50 名用户；按接续需求决定是否增加一种原生移动端；2～3 类具名任务；记忆同步、执行验证与中断恢复 |
| 有限公开版 | 再投入 12～20 周 | 扩大设备兼容与运行监控；计费自动化、升级回归、弱网体验和资料管理达到有限公开服务要求 |
| 合计 | 约 6～10 个月的条件性估算 | 一种桌面平台＋手机网页；证据支持且资源具备时扩展一种原生移动平台 |

阶段应按验收和用户证据推进，不按日历自动扩大。新增平台、复杂数字人资产、硬件或企业交付需另外估算。

设备配对与撤销、任务停止、基本运行记录和数据删除应在真实用户使用前具备；收费和退款路径应在付费试验前可用。它们可以先采用简单实现，不能等到公开版才补。上述 6～10 个月是条件成立后的工程范围估算，不包含无法预知的研究返工、招募等待或更长的续费观察，也不代表商业可行性会在该时间内得到证明。

如果实际只有 1～2 名开发者，应缩减同时推进的系统、活动和工具数量，并降低表现复杂度；仍需保留一个完整、连贯的角色体验。不能直接假定 AI 编程工具会把上述工期按固定比例压缩。

### 13.2 阶段产物

1. **概念阶段**：角色规范、体验原型、技术验证记录、访谈证据与成本初测。
2. **私测阶段**：真实使用日志、任务验收、陪伴体验访谈、跨端失败分析和购买数据。
3. **公开阶段**：支持范围、服务额度、升级与恢复机制、运营流程和平台适配记录。

## 14. 主要风险与应对

| 风险 | 对产品的影响 | 应对方式 |
|---|---|---|
| 新鲜感消退 | 下载和首日互动好，随后无回访 | 观察共同活动与第 3～4 周主动使用 |
| 形态与活动不匹配 | 人物打扰用户或显得多余 | 测试表达节奏、出现位置和安静模式 |
| 人格与记忆漂移 | 用户感到“换了一个伙伴” | 角色版本管理、记忆更正和升级回归 |
| 工具能力不可靠 | 角色亲和却无法交付 | 缩小支持范围，建立真实验收与失败反馈 |
| 跨设备结果不一致 | 重复执行、丢状态、重复回应 | 持久任务标识、状态核对、明确执行权 |
| 端云边界不清 | 用户误以为资料完全在本地 | 明确推理、同步、附件的各自数据流 |
| 平台权限差异 | 某些设备无法达到演示体验 | 逐平台验证，公开支持范围与在线条件 |
| 推理和语音成本过高 | 活跃增长反而扩大亏损 | 记录任务成本、额度和高用量分布 |
| 内容与声像权利不明确 | 角色、音色、内容难以持续商用 | 建立素材来源和使用范围记录，发布前专项核查 |
| 平台功能快速覆盖 | 基础功能难以形成付费理由 | 专注相处方式、活动质量和长期协作体验 |
| 范围持续膨胀 | 同时建设游戏、助手、数字人、硬件与平台 | 以每阶段证据决定扩展，维持清晰产品主张 |

## 15. 趋势判断：哪些可以相信，哪些仍需等待

| 判断 | 证据强度／性质 | 产品意义 |
|---|---|---|
| Agent 正走出 IDE 与 CLI | 已有跨端、跨工具产品 | 不必把目标人群限制在开发者 |
| 语音、人物表现与记忆可以进入同一体验 | 已有商业和开源实践 | 可以开始设计和验证具身伙伴 |
| 手机交办、电脑执行可以产品化 | 已有直接案例 | 是可实现能力，不是天然差异化 |
| 用户会期待更少重复说明与更连续的工作 | 产品推断，需要分人群验证 | 重点测量身份、关系与任务连续性 |
| 同一个伙伴会以不同形态出现在不同设备 | 趋势假设 | 保持身份一致，表达适配设备 |
| 桌宠／数字人会成为所有人的统一入口 | 证据不足 | 不据此进行全面平台投入 |
| 陪伴与执行融合可以带来更高留存与付费 | 核心商业假设 | 需要对照体验与真实交易验证 |

可预期 IDE、CLI、聊天、桌面、手机等入口长期共存。伙伴可以调用这些工具，并在不同情境采用不同交互，不必以替代所有入口作为成功条件。

## 16. 决策建议与下一步

**建议先形成一份有预算上限、责任人和复核日期的概念研究任务书，研究“形态＋共同活动＋有限行动＋双设备连续性”的整体价值。当前报告支持申请这一阶段资源，不代表预算已经获批。**

首先完成以下五项工作：

1. 确定研究人群与一类共同活动，收集真实情境证据。
2. 制作一个具有完整声音、动作和行为规范的角色，验证相处感。
3. 接通一类可检查结果的真实任务，保证人物表达与执行状态一致。
4. 实现电脑与手机之间的身份、记忆和任务接续。
5. 按预先定义的指标比较陪伴、助手和融合体验，核对成本与真实购买。

当前不宜做出市场规模、全面自主性或确定收益承诺。最重要的下一轮证据是：用户是否愿意主动回来与这个伙伴共同活动，以及这段共同经历能否持续产生陪伴价值和实际成果。

## 17. 基础理论复核：这份报告现在能支持什么决策

### 17.1 各框架承担不同问题

NPDP 是 PDMA 的新产品开发专业知识与认证体系，不是一个给项目算出成功概率的公式。本文按其七个领域检查研发经营是否完整，再用商业模式画布、价值主张画布和阶段门落实到本产品。七个领域的命名以 PDMA 官方说明为依据；以下诊断及投资建议属于本报告的应用判断。[方法依据：PDMA NPDP 七领域](https://www.pdma.org/page/certification-central)

| 框架 | 本报告用它回答的问题 | 具体产出 |
|---|---|---|
| NPDP 七领域 | 从战略到退出，产品开发与经营还有什么缺口 | 第 18 章审查矩阵 |
| STP：细分、目标选择、定位 | 广泛机会中，先验证哪一类使用情境 | 候选人群比较与定位假设 |
| 商业模式画布 BMC | 为谁创造价值，怎样交付，谁支付，如何覆盖成本 | 第 20 章九要素与关联检查 |
| JTBD 与价值主张画布 VPC | 用户在具体情境中想取得什么进展，功能与形态如何帮助 | 第 19 章用户任务与价值对应 |
| Stage-Gate 阶段门 | 下一笔资源是否值得投入，凭什么继续 | 第 21 章阶段决策表 |
| 假设实验与 Test Card | 怎样让核心判断接受真实行为检验 | 第 22 章实验与反证条件 |

这些框架相互配合：客户任务决定价值主张，价值主张影响成本与收费，商业假设决定实验，实验结果决定阶段投入。填完框架只意味着逻辑可以被审查，不意味着假设已经成立。

### 17.2 对原结论的三项收紧

**第一，“行业出现这个形态”支持探索机会，不能证明自己的产品值得购买。** 第 3～4 章已证明存在相关能力和竞争。还需要证明目标用户的替代方案存在不足，并愿意因此安装、回访和支付。

**第二，融合必须有同一用户的证据。** 陪伴产品有需求、Agent 有需求，不等于两者相加就产生更好的商业模式。需要观察同一人的相处需求和行动需求是否发生在相容的活动中，融合是否改善体验，以及增加的服务成本能否被收入覆盖。

**第三，当前只足以申请研究与概念试验资源。** 已有生态资料、产品设想和技术分解；尚无一手需求、完整成本、真实续费和可重复获客证据。可以开发验证所需原型，但不能把完整商业开发当作已经通过的决策。

### 17.3 不能被平均分掩盖的条件

本报告不设置“技术 8 分、市场 9 分、综合 85 分”一类评分。原始证据不足时，精确分数容易制造确定感。以下条件需要分别成立：

- 有一个可以明确描述、接触和服务的初始用户群。
- 角色与共同活动产生持续价值，支持范围内的行动能够可靠交付。
- 用户愿意为明确的套餐实际付费，服务成本和额度相容。
- 团队能够长期维护人物、模型、设备与客户关系。

其中某项暂时缺证，可以继续有上限的实验；如果一项关键假设被稳定反证，应调整产品或停止该方向的投入。

## 18. NPDP 七领域审视与战略选择

### 18.1 七领域审查矩阵

以下是本项目的定性诊断，不是 PDMA 官方成熟度评级。

| NPDP 领域 | 已有基础 | 尚缺什么 | 对下一步的影响 |
|---|---|---|---|
| 新产品战略 | 愿景与形态明确；已识别系统厂商、Agent 与陪伴产品竞争 | 初始目标情境、购买理由、团队独特能力与商业边界 | 先形成一页产品创新任务书，避免愿景直接变成全量需求 |
| 产品组合管理 | 有游戏、桌面伙伴、跨端助手、内容生态等候选方向 | 同时做什么、暂存什么、如何分配有限人力的规则 | 主线只验证一个完整伙伴体验；其他方向作为需要独立证据的选项 |
| 新产品开发流程 | 有概念、私测、公开版路线 | 每阶段的商业证据、责任人、资源承诺和退出条件 | 引入第 21 章阶段门，每次只决定下一阶段资源 |
| 文化、组织与团队 | 有四人团队及兼职假设 | 人物设计、研究、客服、成本分析与执行可靠性的实际责任和容量 | 指定责任人并计入工时；一个人兼任多职也必须有容量约束 |
| 工具与度量 | 有任务验收、回访、付费与成本指标 | 统一分母、实验混杂控制、全用户群成本与版本回归 | 建立用户级、任务级、财务级三套互相可核对的记录 |
| 市场研究 | 有公开资料与访谈计划 | 最近真实行为、替代成本、退出原因、真实交易与续费 | 从桌面研究转向用户行为研究，不用兴趣问卷代替需求验证 |
| 生命周期管理 | 已识别升级、记忆和模型漂移风险 | 声像资产续期、供应商停服、套餐变更、记忆迁移与产品退出方案 | 在对用户作持续服务承诺前，先设计可维护、可退出的机制 |

审查说明：当前相对充分的是机会扫描和产品设想，最薄弱的是市场研究、商业闭环与长期运营证据。因此下一步资源应优先减少这些不确定性。

### 18.2 战略：愿景保持宽，初始交易需要具体

STP 在这里用于选择起点，不把长期产品限定为某个职业。按使用情境提出三个候选方向，以下都是研究假设：

| 候选方向 | 可识别的初始情境 | 形态的核心价值 | 主要验证障碍 |
|---|---|---|---|
| A：角色共同生活／娱乐 | 成人在个人电脑前休闲，愿意与固定角色交流或共同体验内容 | 审美、人物表达、相处仪式和共同记忆 | 新鲜感后是否回访，内容生产成本是否可持续 |
| B：共同学习／创作 | 成人反复进行个人学习或创作，需要讨论、鼓励与实际资料处理 | 一起推进事情的搭档感，熟悉的反馈方式与进度记忆 | 同一用户是否同时需要角色与行动，是否愿意持续支付 |
| C：日常事务委托 | 成人经常跨设备处理资料、安排与待办 | 熟悉的沟通入口、可理解的行动状态和连续上下文 | 任务可靠性、权限接受度、系统免费替代与支持成本 |

**建议优先为 B 制作一份完整候选画布，同时保留 A、C 做概念比较。** 理由是共同活动更便于同时观察关系与实际成果，并能提供明确验收物。这是便于学习的研究顺序，不是已有数据证明 B 的市场更大。正式开发前仍需进一步在“学习”或“创作”的一种具体活动中选定起点。

补充顺序：在按 B 招募产品试用者之前，先按基础假设研究识别协调负担、交流缺口及两者重合的人群。B 在本文中仍是画布示例，不能代替前置的需求发现，也不预先排除 A、C 或其他情境。

不能仅招募喜欢桌宠的人，再宣布形态对大众有效；也不能仅招募追求效率的人，再宣布角色多余。需要保留动机、现有工具与使用环境记录。

B 的候选定位可表述为：

> 为反复独自进行个人创作、愿意与固定角色相处的成人，提供一个能共同讨论、记住进展并整理指定资料的跨设备伙伴，让创作过程更有陪同感，也更容易接着做下去。

这句话刻意落到使用情境与结果。是否节省时间、提高质量或增强持续投入，需要分别测量，不能由“使用了 AI”推出。

### 18.3 从竞争结构检查利润空间

按现有竞争、潜在进入者、替代方案、供应商与买方五种力量检查第 4 章资料，可得到以下推断：

| 力量 | 对本项目的判断 | 产品与经营选择 |
|---|---|---|
| 现有竞争 | 模型平台、系统厂商和陪伴产品争夺注意力与订阅预算 | 首次体验就呈现完整相处方式和共同活动价值 |
| 潜在进入 | 组件可组合降低原型进入难度，持续经营仍需要维护能力 | 不把技术拼装当作持久优势；积累角色质量、活动设计与交付记录 |
| 替代方案 | 普通聊天 AI、专用软件、真实同伴或维持原习惯都可能满足任务 | 比较用户整套现有方案的收益、费用和操作负担 |
| 供应商 | 模型、语音、角色资产与分发平台改变条件会影响体验和成本 | 关键能力验证备选方案，并将切换成本计入预算 |
| 买方 | 用户可低成本试用其他应用；长期记忆也可能让迁移变得麻烦 | 用持续价值留住用户，提供记忆管理与退出能力；不依靠数据锁定盈利 |

这表明：生态成熟提高“做得出来”的可能性，同时也可能压缩基础功能的定价空间。产品应验证整套体验的支付价值，并持续关注平台替代。

### 18.4 产品创新任务书与组合管理

建议在研究启动前形成以下任务书。未掌握的预算和人员不代填成已批准事实。

| 项目 | 建议内容 |
|---|---|
| 长期愿景 | 一个能跨设备持续相处和协作的个人 AI 伙伴 |
| 本轮机会 | 验证固定角色参与重复的个人活动是否值得持续使用与支付 |
| 本轮边界 | 一种桌面平台、手机网页、一个完整角色、一类共同活动、一类可验收行动 |
| 核心假设 | 关系有价值；行动有价值；二者对同一用户相互增益；交付成本可覆盖 |
| 可利用基础 | 现成模型、渲染和连接技术；既有项目资产经适配后可作实验材料 |
| 资源约束 | 按实际人员、可投入人日、现金上限和外部依赖登记，当前待确定 |
| 本轮交付 | 用户证据、角色体验原型、任务与接续实测、画布修订、成本账和下一门建议 |
| 保留选项 | 完整游戏、硬件、角色市场、企业版，分别等待自己的用户与经营证据 |

组合管理的重点是控制同时进行的工作。游戏可以独立验证娱乐价值，硬件可以独立验证摆放和持续存在感；它们不应因为共享一个角色，就自动获得同一轮开发预算。原生移动端也应由手机网页试验中的自然需求推动。

## 19. JTBD 与价值主张画布：用户究竟购买什么

### 19.1 从用户情境与进展出发

JTBD 关注人在特定情境中希望取得的进展，包含功能、情感与社会因素。因此，陪伴、审美和身份表达可以成为独立的购买动机；不能只用效率指标衡量数字人。[方法依据：Christensen Institute，Jobs to Be Done](https://www.christenseninstitute.org/theory/jobs-to-be-done/)

以下以 B 方向中的“反复独自进行个人创作”为候选情境；均待访谈和行为研究验证。

| 层次 | 用户任务假设 | 应寻找的真实证据 |
|---|---|---|
| 功能任务 | 把零散材料推进成一份能继续编辑的作品，离开电脑后还能接着讨论 | 最近一次材料、过程和作品；卡在哪里；现有工具如何处理 |
| 情感任务 | 创作中有人接得住想法，停下后再次开始时不感到完全陌生 | 用户最近如何寻求反馈或陪同，哪些互动愿意重复 |
| 社会任务 | 形成符合自己风格的作品，并能自主决定是否让他人看见创作过程 | 真实分享与不分享的原因，角色展示是否合适 |

一个可检验的任务表达是：

> 当我晚上独自整理一篇个人作品时，我希望有一个熟悉的伙伴一起讨论，并帮我把指定材料整理好，这样下次打开电脑或手机时，我既能接上思路，也愿意继续这段共同活动。

“用户想要 Rust、Wasm、长期向量库”不属于这层任务；它们可能是交付选择。“用户一定孤独”也不能作为预设，愿意独自创作与需要治疗或心理干预并不等同。

### 19.2 填写价值主张画布六要素

价值主张画布将客户任务、痛点、收益，与产品服务、痛点缓解方式、收益创造方式对应。下面的匹配仍是假设，需要用真实使用验证。[方法依据：Strategyzer Value Proposition Canvas](https://www.strategyzer.com/library/the-value-proposition-canvas)

| 画布部分 | 候选内容 |
|---|---|
| 客户任务 Jobs | 持续推进个人作品；讨论想法；保持活动和关系连续；自主控制注意力与资料 |
| 痛点 Pains | 工具切换和重复说明；反馈泛泛；独自推进时缺少回应；角色过度打扰；担心错误修改资料 |
| 期望收益 Gains | 熟悉且有风格的共同活动；能继续编辑的成果；回来后接得上；想安静时也自在 |
| 产品与服务 Products & Services | 有声音和身体表达的桌面角色；一类共创活动；指定资料整理；手机接续；可管理记忆 |
| 痛点缓解 Pain Relievers | 经确认的活动记忆减少重复说明；动作预览与结果核对减少不确定；节奏与静默选项降低打扰 |
| 收益创造 Gain Creators | 角色以一致风格共同讨论并回顾进展；表达倾听和等待；跨端延续共同经历与成果 |

### 19.3 三条最重要的对应关系

| 用户期望 | 产品机制 | 验证结果，而非功能上线 |
|---|---|---|
| 相处有回应、值得再来 | 连贯角色、倾听反馈、共同活动和可控出现节奏 | 新鲜感后主动回来，描述具体有价值的相处；记录打扰与关闭原因 |
| 事情真的推进 | 对指定材料的有限执行与可编辑交付 | 用户验收结果，核对返工与人工介入；与原有方法比较 |
| 换设备仍是同一个伙伴 | 身份、约定、活动状态与任务状态接续 | 自然接续时无需重复核心信息，用户理解任务在哪执行 |

应优先验证用户最重视的两三条对应关系。即使每个痛点都有一个功能，也可能因为用户不在意该痛点而没有购买价值。

### 19.4 数字人形态需要分层验证

桌宠、风格化人物和写实数字人的成本、语境与期待不同，不能把“有头像”视为完成形态验证。建议分开观察：

1. **接近意愿**：外观、声音、风格是否让用户愿意开始相处。
2. **在场体验**：倾听、等待、安静陪同、适时回应是否自然。
3. **共同活动**：角色是否以有意义的方式参与，而非重复装饰性台词。
4. **身份连续**：换设备、隔几天回来或模型升级后，用户是否仍感到熟悉。
5. **支付与成本**：哪些表达质量影响付费，哪些复杂度增加制作与运行负担却没有对应价值。

这里的研究问题是选择合适的表现方式、节奏和投入程度。人物、声音与关系设计从第一轮原型就应有责任人和资源，不能在功能开发完毕后临时补一个外壳。

## 20. 商业模式画布：候选 B 的九要素与经济闭环

### 20.1 画布范围

本画布只描述一种候选模式：**向个人用户直接销售共同创作伙伴的软件服务**。使用者、购买决策者和支付者暂定为同一个成年人。企业采购、硬件买断和双边角色市场需要另外画布，不能把它们的客户和收入加在一起制造闭环。

商业模式画布用于检查价值创造、交付与获取的关系；改变客户群时，渠道、关键活动和成本也需要随之变化。[方法依据：Strategyzer Business Model Canvas](https://www.strategyzer.com/library/the-business-model-canvas)

### 20.2 九要素

表内均为产品假设或待建立能力。外部供应商类别不代表已经签署合作。

| 要素 | 候选设计 | 最大未知／需要的证据 |
|---|---|---|
| **1. 客户细分** | 经常在个人电脑独自创作、愿意尝试固定角色、自己付费的成人；先选一种重复活动 | 是否有同一批用户同时需要相处与协作；能否稳定触达；价格是否在其预算内 |
| **2. 价值主张** | 一个熟悉的伙伴共同讨论、记住进展、整理指定资料，并在手机与电脑间延续 | 是否优于现有工具组合；融合带来多少持续价值 |
| **3. 渠道通路** | 用完整活动演示在匹配的创作或角色兴趣社区招募；自有介绍页承接；桌面安装与手机接续完成交付 | 看演示的人是否成为活跃付费者；安装流失和渠道成本；不把视频播放当获客完成 |
| **4. 客户关系** | 自助上手、用户控制的个性化与记忆；试验期明确的人工支持；可预期的订阅与退出 | 人物关系能否持续；人工服务是否过重；退款与流失原因 |
| **5. 收入来源** | 优先试验一个价格与额度清晰的月订阅，包含角色活动、一定语音与具名任务能力；装扮／内容另作可选购买测试 | 哪项价值推动交易和续费；额度是否破坏体验；内容购买是否只是一次性兴趣 |
| **6. 核心资源** | 有可用权利的角色、声音、动作与活动内容；角色规范；执行与记忆系统；研究和运营能力 | 资产取得与续期成本；角色质量能否维持；模型变化后的替换成本 |
| **7. 关键业务** | 设计共同活动；维护角色一致性；运行推理与任务执行；验证结果；管理设备与数据；支持和成本控制 | 内容与客服产能；每新增用户带来的维护工作；可靠性是否随规模下降 |
| **8. 重要伙伴** | 模型／语音服务提供者、角色美术与音色合作方、支付和分发服务方；有需求后再引入内容作者 | 合作条件、可用地区、费用与替代方案；避免依赖单一关键方 |
| **9. 成本结构** | 固定研发与资产制作；持续内容与运营；模型、语音、任务执行、存储和同步；支付退款处理；免费试用、获客与支持 | 完整用户群的用量分布；典型与高成本尾部；订阅是否覆盖持续义务 |

### 20.3 核对九要素是否真正相连

第一条链路是：**重复创作情境 → 固定角色共同活动与资料交付 → 活跃与续费 → 支付持续服务成本。** 若用户只喜欢角色外观并一次性购买装扮，便不能据此证明月订阅成立。

第二条链路是：**活动演示 → 合适用户安装 → 第一次有价值体验 → 持续使用 → 实际购买。** 应按同一渠道和同一批次跟踪。吸引来大量欣赏数字人视频的人，也可能没有带来软件用户。

第三条链路是：**角色承诺与任务承诺 → 内容／工程／运营活动 → 相应资源与成本。** 若承诺稳定声音与共同记忆，便必须承担授权、模型变更与记忆维护；不能只计算生成几句话的费用。

建议使用以下管理口径；数值均待实测：

```text
整批用户服务贡献
= 该批用户在观察期的经退款调整收入
− 该批全部用户的推理、语音、执行、同步、支付与直接支持成本
  （包括免费、未转化、退出用户，以及失败和重试）

该批获客后的贡献
= 整批用户服务贡献 − 该批可归属的获客投入

渠道 CAC
= 同一批次、同一归因口径的获客投入 ÷ 该批新增付费用户数

获客回收时间
= 累计服务贡献首次覆盖该批获客投入所需的时间
```

没有新增付费者时不能得到可用的 CAC；广告、创作者合作、素材制作和可归属的招募人工都应记录。研究招募成本与规模获客成本分别标注，避免把朋友试用或研究补贴当作可复制渠道。

经营层面还要扣除持续内容生产、固定研发、资产授权和公共运营费用。同一笔成本只归属一次。若采用简化的稳定经营模型，可用“当期全部用户服务贡献能否覆盖持续获客与固定运营投入”检查盈亏平衡；这需要实际用户结构，不能只拿一个典型付费用户外推。

当前没有留存曲线和续费数据，不计算确定的 LTV，也不直接套用某个 LTV/CAC 倍数作为达标证明。短期可观察到的累计净贡献，比假设无限续订得到的终身价值更有用。收入确认和税费的正式财务处理应在商业落地时另行确定，本节仅用于产品经营比较。

### 20.4 关键敏感性

| 变量 | 应作的情景检查 | 会改变什么决策 |
|---|---|---|
| 语音／视觉用量 | 根据实测分布比较常规与高用量用户 | 套餐额度、默认交互和模型选择 |
| 任务成功与重试 | 比较包含所有失败成本的验收单价 | 扩大或收缩工具范围 |
| 模型或音色成本变化 | 用供应商实际报价和备选方案重算 | 价格、服务组合、迁移预算 |
| 角色内容与支持工时 | 纳入实际制作、解释、退款与故障处理时间 | 更新频率、组织配置、可服务人数 |
| 付费与续费 | 按真实可续费用户计算，记录退款和暂停 | 是否值得扩大获客；不能用首月收入替代 |

具体情景值应来自试验和报价，本文不编造市场价格、转化率或毛利率。

### 20.5 哪些还不能称为壁垒

聊天、模型接口、动画角色、长期记忆和手机发任务目前都是产品能力组合。仅拥有这些模块，不足以保证独特性。可能积累的优势是经过验证的角色与活动设计、稳定的交付体验、可持续内容生产以及匹配用户的渠道；目前均需要建设。

个人使用记录增加，可能帮助个性化，但并不自动形成网络效应。只有当新增参与者能持续给其他用户或创作者带来可测的额外价值，才有理由讨论网络效应。角色市场的供需、质量与分成应在独立验证后再投入。

## 21. 用 Stage-Gate 管理投入，而非按功能清单自动升级

Stage-Gate 将项目工作阶段与资源决策门区分：每门审查交付物、判断依据和下一阶段资源，并可作出 Go、Kill、Hold 或 Recycle。以下流程是面向本项目的轻量化改编，不是 NPDP 要求所有软件项目执行的统一模板。[方法依据：Stage-Gate Discovery-to-Launch](https://www.stage-gate.com/about/stage-gate-innovation-performance-framework/discovery-to-launch-process/)

### 21.1 当前阶段与后续决策

| 阶段及决策门 | 本阶段应消除的主要不确定性 | 门前可审阅证据 | 通过后只释放什么资源 |
|---|---|---|---|
| **发现与范围界定 → G1** | 是否存在值得研究的机会，研究边界是否合理 | 第 3～8 章生态资料、候选情境、创新任务书、研究预算上限与责任人 | 一轮一手研究和验证原型；当前已具备初步资料，预算与人选尚待落实 |
| **概念与商业论证 → G2** | 谁需要什么，角色／行动如何匹配，是否有可行交付路径 | 行为访谈、完整体验原型、九要素画布、真实设备记录、成本初测、私测方案 | 试验产品建设、内部验证与受控原型可用性测试；持续真实用户私测及交易探索由 G3 放行 |
| **试验产品与服务准备 → G3** | 是否能够对真实用户履行有限承诺 | 支持范围、任务核对、设备撤销、记忆管理、升级恢复、支持安排；收费前完成购买退款流程 | 开始有记录的有限私测及交易探索 |
| **用户与商业验证 → G4** | 新鲜感后是否有重复价值，价格与交付成本是否相容 | 用户级主动使用、任务验收、购买与退款、至少覆盖实际续费机会的随访、新用户复测、完整批次成本 | 有边界的公开服务准备或继续补证；不直接扩大为通用平台 |
| **有限发布与上市后复盘 → G5** | 获客、交付和续费能否重复，团队能否承受维护 | 分渠道用户批次、续费与贡献、支持负荷、模型变更记录、扩容或收缩方案 | 逐步扩大渠道、平台或活动；每项重大扩展重新审查 |

角色与执行能力可在各阶段内并行迭代，用户研究也持续进行。阶段门用于决定是否增加投入，不要求每个细节一次性确定。第 13 章是工程工作量估算，本表是投资证据要求，两者不能互相替代。

### 21.2 四种门决策

| 决策 | 适用情形 | 必须留下的记录 |
|---|---|---|
| Go：继续 | 本阶段关键证据足够，下一步价值与风险可接受 | 下一阶段范围、人日、费用上限、责任人和复核日期 |
| Hold：暂缓 | 机会仍可能成立，但资源或外部条件暂不具备 | 等待条件、保留成本与重新评审时间；不能无限挂起 |
| Recycle：返回补证／修改 | 关键假设仍不清楚，或问题可通过特定调整解决 | 要修正哪项假设、做什么试验、花费上限与停止条件 |
| Kill：停止该方向 | 核心需求反复不成立，或在可接受条件下无法交付和经营 | 停止原因、资源释放、用户和资料收尾；保留研究学习 |

阶段负责人提交证据，产品、技术、角色体验和经营责任人共同评审；人数少时可以兼任，但应把事实、解释和最终决定分别记录。不能由“已经投入很多”成为继续投入的主要理由。

### 21.3 对原试验与排期的修订要求

8～12 次广泛访谈用于发现线索，不能证明所有候选细分已研究充分。出现不同购买动机或相反反馈时，应在选定情境继续访谈；后续样本数量取决于新信息和决策需要。

四周试验安排在可用产品和服务准备完成后开始。开发、招募与观察可以部分重叠，但不能在产品持续不可用时把日历天数当作有效使用周期。原计划的 30 人比较主要为探索；新的独立用户和实际续费机会用于减少熟人、补贴和新鲜感带来的偏差。

第 12.4 节的 6/10、80%、3/10 等数字是候选观察信号。一个人就会改变每组约 10 个百分点，因此评审必须结合具体行为、失败原因与成本，不以分数平均或单项达线替代判断。

设备配对、撤销和任务停止在真实使用前验证；简单购买与退款在收费前完成；公开阶段增加自动化、规模和兼容性。计划新增原生移动端时，应先说明手机网页暴露了什么实际限制，以及该限制值得多少投入。

## 22. 核心假设、实验与指标设计

### 22.1 把商业画布转成实验记录

Test Card 的实用部分是事先写清假设、测试方式、测量指标和判断门槛。以下表格据此为本项目设计；不是已执行实验。[方法依据：Strategyzer Test Card](https://www.strategyzer.com/library/validate-your-ideas-with-the-test-card)

| 假设 | 试验及要测的证据 | 什么结果会要求修订 |
|---|---|---|
| H1：存在可识别的重复情境 | 回看最近真实活动及替代方案，观察用户是否愿意带自己的材料再次尝试 | 只有泛泛喜欢、没有近期活动或替代缺口；无法找到共同情境 |
| H2：形态具有持续相处价值 | 完整角色参与同一类活动，记录新鲜感后的主动回访、安静模式选择和具体体验 | 只在首日看外观，持续关闭角色；经过节奏／风格修正仍无主动相处 |
| H3：融合为同一用户增加价值 | 探索三种整体体验，再在选定人群复测；分别记录陪伴、行动与共同价值 | 两类能力分别使用却互相干扰，或融合没有用户重视的收益 |
| H4：跨设备连续性有价值 | 先用桌面与手机网页，观察自然离开电脑后的接续，不要求为了试验而换设备 | 有充分真实机会但用户仍选择不用；若机会不足则记录缺证而非失败 |
| H5：用户愿意为可交付套餐支付 | 公布价格、额度、支持范围与退款方式，观察真实购买、使用后反馈及可续费者行为 | 只在免费或补贴时使用，退款集中于核心承诺，或额度一明确就失去支付意愿 |
| H6：经营与交付可持续 | 记录整批用户消耗、支持和失败；用实际供应商及角色成本重算 | 高活跃带来持续亏损，且可接受价格／额度下无法改善 |

H1、H2、H3 和 H5 对方向选择影响最大；任务可靠性和设备边界属于开展真实行动试验的前置条件。技术可以先做有界验证，但不应等到大部分平台开发完成才研究这些假设。

### 22.2 三个优先执行的实验

**实验一：真实活动与替代方案访谈。** 先比较 A、B、C 的实际情境，要求用户回看最近一次活动，展示现有流程和付出。输出用户选择某种方案的原因、何时需要角色、何时需要行动，以及不用产品的理由。若没有重复情境，返回调整目标场景。

**实验二：完整角色参与的四周探索。** 使用第 12 章方案，但保留所有招募者的去向，记录功能、价格、支持和版本差异。除三组整体比较外，重点分析融合组内同一用户的行为。若要进一步声称形态产生因果提升，需要另行设计可比条件、分配方式和样本量；不能直接从这轮小样本得出结论，也不宜让用户短期频繁切换关系模式后视为无残留影响。

**实验三：明确套餐的付费与接续试验。** 在已有可用服务基础上观察真实购买，并跟踪到实际续费机会；可将两个续费机会作为下一轮随访规划起点，周期仍随套餐而定。对自然发生的手机接续记录是否完成、上下文是否要重讲、带来多少额外成本。若用户愿意为角色相处付费却不需要远程执行，应收缩后者而保留前者；若用户只购买内容包，应另验内容经营模式。

具体研究招募、收费和外部沟通属于后续执行事项；本文没有开展这些动作。

### 22.3 指标分母与反向指标

| 维度 | 主指标口径 | 必须同时观察 |
|---|---|---|
| 激活 | 同一招募批次中完成首次有价值活动的人数／全部招募人数，并另列未安装、安装未用 | 安装负担、首次失败、研究人员帮助 |
| 关系与陪伴 | 第 3～4 周主动回访且能描述具体价值的人数，保留原始人数 | 打扰、主动收起、负面互动、因补贴而使用 |
| 行动 | 范围内意图、受理、执行、交付、验收分别计数 | 任务难度、拒绝、返工、耗时、人工救援与虚假完成 |
| 融合 | 同一用户连续使用两类能力且说得清共同收益 | 是否只因被要求测试，是否互相干扰 |
| 跨设备 | 实际具备接续机会、发起尝试与成功接续分别计数 | 重复执行、断连、重复说明、设备电量与在线要求 |
| 支付 | 购买人数／看到同一真实报价的合格用户数；另外报告整体招募转化 | 优惠、研究补贴、退款、价格与功能差异 |
| 续费 | 在同一周期内实际发生续费的人数／有续费机会的人数 | 暂停、退款、扣款失败、仍未到续费日；付款不替代实际使用 |
| 经营 | 全部用户批次贡献、渠道成本与回收进度 | 免费消耗、高用量尾部、内容制作与直接支持 |

分析时同时保留用户级和任务级结果。例如，同一名高频用户完成 20 个任务，说明该用户有重复价值，但不能替代 20 位不同用户的需求证据。任务验收率变高，也要检查是不是通过拒绝更多任务或增加人工干预得到的。

### 22.4 学习成果应改变决策

每轮形成一张学习记录：原假设、观察事实、与假设不符之处、证据限制、决定改变什么、下一次验证什么。负面反馈不能全部归因于模型还不够好；需要区分模型问题、角色与活动不匹配、需求不足以及价格不成立。

若陪伴独立成立，可以发展陪伴产品；若协作成立但特定数字人风格不适配，先调整形态和情境；若融合成立但跨端低频，可以先经营桌面体验。以上是不同战略结果，不要求所有能力必须同时成功。

## 23. 组织、生命周期与最终投资判断

### 23.1 责任配置是交付可行性的一部分

| 责任 | 本产品特别需要承担的工作 |
|---|---|
| 产品与研究 | 目标情境、访谈、价值主张、范围、实验与门决策材料 |
| 角色体验 | 外观声音与动作协调、行为规范、共同活动、关系连续性与打扰控制 |
| 技术与交付 | 模型、工具执行、结果核验、设备接续、权限与数据流、变更回归 |
| 经营与运营 | 套餐、费用、内容产能、支持、退款、供应商和服务退出 |

四人计划只有在这些责任有实际容量时才成立。产品设计人员无法默认同时承担无限的研究、剧本、社区、客服和数据分析。外包美术、音色与测试也需要明确交付范围、工时、费用和协调时间。

### 23.2 生命周期不能只写“持续迭代”

| 生命周期事件 | 对用户的实际承诺与处理要求 | 应记录的成本／验证 |
|---|---|---|
| 初次使用 | 明确角色和任务支持范围，允许逐步建立记忆与设备连接 | 首次体验、失败率与支持时间 |
| 稳定相处 | 角色行为一致，共同活动有变化，用户能够决定出现节奏 | 内容更新、人群差异、重复价值与打扰 |
| 模型／声音升级 | 核对声音、语气、记忆和行动表现，解释显著变化 | 回归样本、失败恢复、替换服务成本 |
| 换设备或版本 | 记忆、约定与任务有可理解的迁移结果 | 同步冲突、损坏恢复、设备撤销 |
| 角色或合作内容变更 | 说明可继续使用的范围和替代方案 | 资产权利期限、维护义务和再制作预算 |
| 用户取消或离开 | 取消订阅、停止后台动作、可管理记忆和资料 | 退款处理、导出删除、凭据撤销 |
| 产品收缩或停止 | 完成必要通知、处理未完成任务与服务义务，提供可行的数据交付路径 | 收尾人员、存储与支持预算 |

这些是持续经营设计要求。具体发布地区与渠道确定后，应对照当时适用的规则和合作条款核查；本文没有据此给出法律结论。

### 23.3 用基础理论复核后的决策

| 决策项 | 当前建议 | 理由 |
|---|---|---|
| 是否研究桌面搭子与数字人 | 继续，作为核心产品价值研究 | 形态、相处与身份连续具有独立的体验空间 |
| 是否继续跨设备愿景 | 保留，用低成本双端接续先验证 | 技术已有基础，自有用户的频率和支付价值未证实 |
| 是否直接投入通用 Agent 平台 | 暂不进入 | 用户范围、交付边界、经营证据不足 |
| 是否只做 SRE／图谱方向 | 不作为前提 | 现有资产不能替代市场选择，用户已明确要求通用品类分析 |
| 是否承诺游戏、硬件和角色市场一起上线 | 暂存为独立选项 | 各自具有不同的买家、运营、成本和验证门 |
| 现在值得投入什么 | 一手需求研究、一个完整角色活动原型、有限任务验证、真实套餐试验准备 | 这些投入直接减少最关键的不确定性 |

**目前最合理的产品立项表述是：申请一轮受预算约束的“跨设备 AI 伙伴”概念与商业验证，验证固定角色、共同活动与有限行动是否对同一类用户形成持续且可支付的价值。**

下一门需要交付：选定情境与用户证据、经修订的九要素画布、可体验的完整角色、可核验的行动与接续记录、实际成本，以及有边界的付费试验方案。获得这些证据后，再决定继续融合、调整形态或场景、收缩跨端范围，或停止某条路线。市场成功与长期盈利仍需后续实际经营证明。
