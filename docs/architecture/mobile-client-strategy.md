# 手机入口：Web优先，App与小程序可接续

2026-09-21。项目发起人已选择手机Web作为第一版。本文记录入口策略，不代表手机产品已经实现；账号接口实际进展见[协调服务](../status/coordinator-auth-api.md)。

## 产品定位与交付顺序

手机承载同一个伙伴的轻量角色表现、交办、状态查看、必要确认与撤销。电脑负责本地资料及明确授权范围内的动作。三种入口共用服务端账号、companion_id、资源归属和授权规则，用户不因入口变化获得另一只伙伴。

| 入口 | 先解决的问题 | 实施顺序 |
|---|---|---|
| 手机Web | 通过链接进入，验证登录、配对、交办与结果查看 | 第一版；React/TypeScript，先验证前台流程，再评估PWA安装与通知 |
| App | 用户持续使用后，对启动、语音、通知和设备集成提出的需求 | 后续按留存与体验证据立项，届时决定原生或跨平台方案 |
| 小程序 | 特定平台内的触达与轻量使用 | 后续根据目标用户渠道选择平台，单独验证登录、通知及角色表现 |

本轮不同时开发三套界面，不为未实施App/小程序创建空目录。角色身份及状态契约可复用；渲染、交互、通知、凭据存放与登录回调按平台适配，不承诺一套UI直接运行所有环境。

## 共用协议与端差异

- 账号接口用HTTP JSON传输，伙伴/任务ID和版本语义与入口类型无关，不依赖Tauri IPC、浏览器localStorage或微信openid。
- 浏览器前台可以拉取状态；重新进入页面必须重新核验会话并补齐服务端状态。后台通知只提示更新，不能承担执行队列或事实存储。
- 手机先显示伙伴、连接设备、待办及需要决定的动作。Live2D移动渲染单独验证性能与素材许可，首版可以使用轻量角色，保留伙伴身份与表达连续性。
- Web凭据策略与真实登录页面一起实现；公开配置可以在前端，管理密钥、模型Key不可进入前端。长期会话不得通过URL/二维码传递。当前协调API没有Cookie或CORS通配认证，Web接入时明确同源代理/BFF及刷新策略。
- App、小程序以后通过相应平台认证适配器接入同一内部账号。平台用户标识只在该来源内有效；绑定已有账号需要双方证明，不能按相同昵称、客户端account_id或未验证邮箱自动合并。
- 登录不等于配对，不等于批准动作。手机/桌面设备授权仍由T44/T21实现；每端各有可撤销会话和设备授权。

## 第一版准出

1. 真实账号在电脑与手机Web登录后获得同一companion_id；两账号交叉访问被拒绝。
2. 配对信息短时有效且一次性，用户能核对电脑和权限；撤销覆盖旧会话、排队及重连。
3. 手机交办后显示真实进度；电脑离线显示等待，不伪装已经执行。
4. 必要确认绑定具体动作、参数和版本；重复确认不会产生第二份产物。
5. 页面重开与网络恢复不会使状态回退；未知结果需要核对，删除记忆不会被旧快照恢复。

桌面本地陪伴继续无需账号。涉及手机、云端及远程授权时再进入登录流程。第一轮先完成账号与HTTP隔离验证，之后按[跨端实施设计](device-continuity.md)接设备授权及手机界面。
