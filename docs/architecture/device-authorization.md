# T44/T21：配对与动作授权协议

2026-09-27。配套[手机接续总体设计](device-continuity.md)、[交付记录](../status/device-pairing.md)。已落地配对闭环、动作授权内核及[文档确认与受限执行](../status/remote-document-confirmation.md)。通用远程执行尚未开放。

## 信任与权限

账号认证、设备关系、单次动作授权分开检查。账号来自认证适配器，不能由请求填写 owner。设备 ID 由服务端生成，绑定账号与当前会话；设备名称由用户填写，不代表硬件证明。重新登录不会自动继承旧设备权限，需要重新配对。保留原有账号共享待办的语义：查看/记录待办不依赖配对，不会触发执行。

当前只有 `document_excerpt` 一种范围，不能通过请求扩大到命令执行、任意文件、聊天或记忆。配对本身不授予某个文件的访问权；本机通过用户文件选择取得文本快照、登记资源 ID/版本，再为具体摘录申请确认；手机不能提供磁盘路径。

## 配对流程

1. 已登录电脑请求 `POST /v1/pairings/offer`，提交 1～40 字设备名称。服务端使用 UUID v4 的随机字节，经拒绝采样生成均匀的六位 ASCII 数字配对码（000000～999999，按字符串保留前导零）；事务内避免与同账号尚存摘要的配对码碰撞，五分钟有效，并限制在当前会话绝对有效期内；同一电脑会话重新生成会使所有先前待确认码失效。
2. 同账号另一会话通过 `POST /v1/pairings/preview` 提交配对码。仅核对，不消费码；返回电脑标识、名称、固定范围及有效期。
3. 手机明确确认后调用 `POST /v1/pairings/accept`，提交配对码、刚核对的 pairingId 和手机名称。服务端事务中重验账号、发起端有效性、时间和状态；绑定控制端、递增授权版本、清除码摘要。相同会话、自身配对、跨账号、超时和重放均拒绝。
4. 两端通过 `GET /v1/pairings` 获取账号内关系及当前会话角色；任一已认证的同账号会话可管理并撤销遗失设备的关系。`POST /v1/pairings/{id}/revoke` 要求当前 revision，防止旧界面覆写新状态。

当前使用六位数字输入配对码，没有扫码、摄像头访问或含长期令牌的二维码。配对码仅在首次响应和当前界面内存中存在；数据库只存 SHA-256 摘要，消费、重新生成或撤销后清除摘要。列表不返回码/摘要或会话 ID。配对记录每账号最多 100 条，暂不自动压缩历史。

六位码的核对与确认共用账号级失败预算：首次失败起固定五分钟窗口，累计五次后返回 HTTP 429 `pairing_rate_limited`，窗口结束前正确码也不接受。错误格式、无效码及不匹配的 pairingId 均计数；成功、换码和重新登录不重置。计数保存于 SQLite `pairing_code_limits`，并发操作串行核对，拒绝请求仍提交失败计数；服务重启后继续生效，时钟回退时拒绝尝试。此错误独立于邮箱验证码的冷却限制，客户端不据此退出登录。

接受配对响应丢失后先刷新列表核对；已消费码不能重新提交“补一次”。只有列表证明确未建立关系时才生成新码。桌面/手机界面使用请求代际与卸载检查，退出、撤销或后续操作后，迟到读取不覆盖新状态。

## 单次动作授权内核

该部分位于 `companion-core` 契约与 `companion-storage`，由受限文档 HTTP 和 Tauri 适配器调用；实际文件写入仅由桌面执行器完成。

| 操作 | 允许的调用者 | 核对及结果 |
|---|---|---|
| 登记/更新资源 | 配对中的电脑会话 | 资源 UUID、严格递增版本、启用状态；更新使旧动作失效 |
| 准备动作 | 配对中的电脑会话 | actionId、resourceId、resourceVersion、规范化参数的 SHA-256 摘要、pairRevision、scope；有效期最多五分钟 |
| 明确确认 | 配对中的手机会话 | 与准备记录完整一致、配对和资源仍有效；待确认 → 已确认 |
| 动作准入 | 原电脑会话 | 再次核对账号/两端会话/关系/资源版本/摘要/有效期；已确认 → 已准入，只允许一次 |
| 撤销关系/更新资源 | 同账号管理会话 / 原电脑 | 尚未准入 → cancelled；已准入 → cancel_requested |

动作 ID 同账号唯一，不能通过修改参数重用。确认和准入不是执行回执；准入后响应丢失必须查询授权状态与本地执行台账，禁止直接重新准入或盲目执行。动作记录每账号最多 500 条，未实现归档。

所有核对和变更在 SQLite `BEGIN IMMEDIATE` 事务中，撤销与准入存在明确提交顺序：撤销先发生则拒绝准入；准入先发生则记录请求停止。`cancel_requested` 不代表副作用已停止或回滚。文档执行器已接入动作前重查、产物核对和完成回执；最终核对之后的停止请求可能晚于文件发布，需要报告实际结果。

## 会话与数据迁移

每次操作重验本机会话；配对双方检查服务端撤销、绝对过期和自有会话的 30 分钟空闲过期。伙伴身份可在重新登录后保持一致，配对权限不自动恢复。失效关系在查询时呈现 expired；后续准入始终重新检查，不能信任上一次列表。

协调数据库 schema 2 → 3 增加配对/授权，3 → 4 增加共享文档；保留已有账号、伙伴、会话、共享待办和配对。4 → 5 增加短码失败预算表，并撤销全部 pending 配对、清空旧长码摘要、递增其 revision；active 配对和文档授权保留。服务端、桌面与手机页面需一同更新，旧码重新生成。文档执行使用独立本地台账，不迁移原本机文档数据。旧程序会拒绝更高版本数据库，不可手改 user_version 降级。

当前手机 BFF 开放配对列表/核对/确认/撤销及文档列表/确认/取消；不开放生成码、文档提交、动作准入和完成回执。Rust 桌面仅访问回环协调 API，Tauri 权限只授予主面板。仍需后续正式 HTTPS 部署、稳定设备密钥、在线能力与事件流设计。

## 文档适配协议（schema 4）

- 电脑 `POST /v1/documents` 原子提交资源快照、授权和预览；只允许当前配对桌面角色。请求为 pairingId、binding、sourceName、preview，不接受 owner、路径或任意动作类型。重复 actionId 仅接受完全相同内容。
- 参数摘要为 `SHA256("remote-excerpt-v1\0" + sourceName + "\0" + preview)`，产物哈希为预览 UTF-8 字节的 SHA-256。资源版本固定为 1；修改内容需新任务。前端不构造电脑分享摘要。
- 双端 `GET /v1/documents` / `GET /v1/documents/{actionId}` 仅返回本会话参与的记录。同账号第三个会话可以管理撤销设备，但不能借此读取摘录或确认动作。
- 手机 `POST .../confirm` 提交完整 binding；电脑 `POST .../admit` 也提交同一 binding。每次重验角色和全部绑定；准入状态只能消费一次。随后电脑再次查询授权，仍为 admitted 才开始写草稿。
- 两端可 `POST .../cancel`，请求为空对象。手机网页提供该按钮，桌面目前通过撤销配对停止未开始的动作。
- 电脑 `POST .../receipt` 提交 binding、state、artifactHash；仅接受 completed/failed/unknown，且先前必须已准入。同状态回执幂等；completed/failed 为终态，unknown 可核对后更新。撤销不会抹掉已完成结果。

本地 `remote-jobs.db` 保存不变的准备数据和分享/准入阶段；`executions.db` 复用执行尝试与产物台账。手机记录必须与本地保存的配对、绑定、文件名、预览、产物哈希全部一致。没有本地意图记录的服务端任务不会执行。轮询通过账号互斥锁与退出串行化；关闭面板仍可处理已分享的任务。

准入响应丢失时，服务器已准入而本地未开始的任务会保守取消并报告失败；不能根据查询到 admitted 就重新开始保存。已发布产物通过重开执行台账与文件核对补回执，每个动作只对应一个固定新文件。当前使用 HTTP 轮询（含设备心跳，见下节），尚无 WebSocket 和恢复备份后的跨服务执行锁。

## 设备心跳与在线状态（2026-09-27）

- **路由**：`POST /v1/devices/heartbeat`（gated：认证 + 16 并发 + 16KB body 上限）。请求体 `{capabilities: string[]}`（原始列表 ≤8 项，每项必须匹配 `ActionScope::slug()`，未知 slug/超限/未知字段 → 400）。返回 `{"updated": bool}`——已登录但从未配对的会话没有设备行，幂等返回 false。
- **租约模型**：`paired_devices` 新增 `last_heartbeat`（可空）与 `capabilities`（canonical slug JSON，排序去重 ≤8）。**读取时推导** `desktop_online = live() && now-last_heartbeat ≤ 15_000`（未来时间戳按不在线处理，镜像 last_seen 防御）；`last_heartbeat` 即使过期也如实返回供"最后联系"显示。
- **约定超时**：桌面 5s 心跳（**独立 tokio 循环**，与 remote-documents 同步循环分离——同步的串行文档调用各带 12s 超时，若共用 tick 会把心跳推过 15s 租约造成假离线闪烁）+ 租约 15s（3 次漏拍）+ 手机 10s 轮询 ⇒ **判离线最坏 25s、恢复在线最坏 15s**。协调器挂起时心跳请求本身最长 12s，但同一协调器上的手机读取也会失败并显示无法连接横幅，不产生假离线。被杀/断电/断网/优雅退出统一由租约到期覆盖（无 /offline 主动下线路由——`RunEvent::Exit` 中 block_on HTTP 是已知脆弱点；logout 由会话撤销兜住）。心跳与同步两个循环各只在自己的请求期间持有账号锁（最坏各 ≤12s），不再叠加阻塞 UI 命令。
- **不延长清单**：心跳只写 `paired_devices` 两列——不写 `paired_devices.expires_at`、不写 `device_pairings`、不写 `action_authorizations`、不动令牌绝对有效期。**display-only**：`desktopOnline` 永不参与 confirm→admit 或任何授权决策。
- **行为变化（有意）**：心跳经 `auth.verify()` 必然刷新 `native_tokens.last_seen` ⇒ 登录且运行中的桌面不再 30 分钟闲置过期（只剩 24h SESSION_TTL）——这正是"在线"的正确语义。
- **既有约束**：`paired_devices.expires_at` 在行创建时冻结（≈min(24h, 创建+30min)），在线展示窗口受配对 ≤30 分钟绝对有效期约束；长期设备身份/配对续期仍在 T21 积压。
- **混跑表现**：Rust `Pairing` 新字段全部 `#[serde(default)]`、TS 解码缺字段降级为 null/null/[]（旧协调器 → 手机不渲染 presence 行而非报错；旧手机对新字段直接忽略）；旧桌面不发心跳 → 恒显示离线。`ACTION_SCOPES`/`slug()` 是能力 slug 的单一事实源——桌面发送与协调器校验直接引用 Rust 常量；手机的 `capabilityLabels` 是 TS 侧手写映射（无法跨语言引用常量），开集回退显示原始 slug 兜底。
